# Tribune 観察事項リスト

## このファイルについて

Tribune の運用中に神山さんが発見した改善点・違和感・将来の Sprint 候補を
体系的に記録する。Code が新しい Sprint 着手時に **前提情報** として参照する場所。

### 位置づけ

- `docs/themes.md` が「テーマプール」、`data/monthly_pivotal.json` が
  「週次選定の結果」なら、本ファイルは **「運用フィードバックの貯水池」**
- 朝刊レビュー時に「これ気になる」と思ったことを軽くメモする場所
- 月次レビュー / Sprint 着手判断時に Code が一括参照

### 更新ルール

- 新規観察は「未着手」セクションに追記
- Sprint 着手で「進行中」へ移動、完了で「完了」へ移動
- 各エントリには **発見日 / 観察内容 / 検討案 / Sprint 候補 / 関連 commit / 状態** を記録
- 該当 commit が無い段階では `-` のままで OK
- 神山さんの自由追記欄として各エントリ末尾に余白を残す
- 個別案件を横断する教訓は「パターン」セクションに記録する（未着手→進行中→
  完了のライフサイクルに乗らないため別枠。Code が着手時にまず読む前提情報）

### 既存 ID 系列との関係

- Code 着手案件番号（C36 / C42 / …）は **着手時に振られる連番**
- 観察事項は着手前の段階を含むため、本ファイルでは **見出しで識別**
  し、関連する C 番号があれば「関連 commit」欄で参照する

| C180 | `data/monthly_pivotal.json` の `article.angles_hints`（曜日別の角度指示）。`monthly_pivotal.py` の docstring にフィールドとして明記され、W1 以降 14 週分すべてに丁寧に書かれていた | **読むコードが存在しない**。`_build_user_message` は `angles_hints` を渡しておらず、角度指示は週によらない `ANGLE_INSTRUCTIONS` だけで駆動していた。14 週分すべて死にデータ（→ C181 で配線予定） |

- **共通構造**:

  * 仕組みの存在が、**コードの呼び出し関係ではなく** docstring・コミット
    メッセージ・設計メモに書かれている
  * 書かれた時点では正しかった、あるいは正しくなる予定だったが、検証され
    ないまま前提として扱われ続けた
  * **grep しても引っかからない**（依存が「コードに現れない」）
  * 後続の改修（C155 / C161 の候補プール変更など）で前提が崩れても
    気づけない

- **特に危険な条件: 滅多に発火しない安全装置**

  C24 の診断ファイルは「fallback 時に原因を追う」ためのもので、**fallback が
  3 ヶ月起きなかったため壊れていることに誰も気づかなかった**。平常時に動作が
  見えない仕組みは、定期的に発火させるか起動時に存在確認しない限り、壊れて
  いても検知できない。

- **教訓**:

  1. 「動くはず」の仕組みは、**実際に発火させて確認するまで存在しないもの
     として扱う**
  2. docstring に書かれた依存関係・保護機構は、テストかコード上の呼び出しで
     裏づけが無ければ信用しない
  3. 改修で前提が変わりうる箇所は、docstring ではなく**テストで固定する**。
     好例は C161 の `tests/page5/test_ai_kamiyama_selector.py`
     「a13 score 999 の確定枠は絶対に選ばれない（除外の構造的保証）」——
     スコアをあり得ない値にして、除外が効かなければ必ず落ちるようにしている
  4. 調査時、「収録されている / されていない」の判定は**複数経路を潰して
     確認する**（C170 の誤診は単一の grep に依存したことが原因。C172 では
     artifact `path:` / `git add` / `.gitignore` の 3 経路を個別に確認した）
  5. **データを書いたら、それが実際に消費される所まで発火させて確認する**。
     C180 は `angles_hints` を書いた直後にプロンプトを組み立てて中身を検査した
     ため、投入当日に気づけた。「書いた → 効くはず」は前提にしない

- **関連**: C161（Chesterton's fence —— 旧構成の制約が「なぜ在ったか」を
  廃止理由と別に確認する）と同系統。C161 が「柵を撤去する前に理由を確認する」
  なら、本項は **「柵があると書いてあったが実際には建っていなかった」**。

- **状態**: パターン記録（個別案件は C168 / C171 / C172 にそれぞれ記録済み）

### 同日 2 回実行で履歴が二重記録される — schedule 遅延が引き起こした

- **発見日**: 2026-08-29（C184 調査中）/ **対処**: C185

  #### 事象

  2026-08-28、GitHub Actions の schedule が **+8 時間遅延**し、神山さんの手動
  実行の**後**に発火した:

  ```
  2026-08-27T23:39Z  workflow_dispatch  success   ← 手動（08:39 JST）
  2026-08-28T01:37Z  schedule           success   ← 遅延発火（10:37 JST）
  ```

  結果、同じ日付で 2 回生成が走り:

  * `archive/2026-08-28.html` の commit が 2 本（`e75a5e7` → `451ff45`）作られ、
    **紙面が丸ごと差し替わった**。朝に読んだ紙面が昼には別物になっていた

    | | 1 回目（09:0x JST） | 2 回目（11:0x JST） |
    |---|---|---|
    | 概念 | スピノザ | 遺伝的アルゴリズム |
    | 料理 | 夏なすと鶏むね肉の洋風白ワインハーブ蒸し煮 | 夏きゅうりとわかめの韓国風薄塩ナムル |
    | 3 面 SER | axismag 718593 | axismag 718611 |

  * `concept_history` / `cooking_history` / `page5_history` に同じ日付が 2 件
    記録された（いずれも `.append()` 実装）
  * `page1_v3_history` **だけは無傷**。`save_essay` が「同日エントリは差し替え
    （再ラン耐性）」を最初から持っていたため

  #### 対処 (C185)

  1. **3 つの履歴を upsert 化** —— `save_essay` と同じ「同日エントリは差し替え」に
     揃えた。日付キーは `concept_history` / `page5_history` が `displayed_on`、
     `cooking_history` が `date` と揃っていないので、各々のキーで判定する
  2. **workflow に二重実行ガード** —— checkout 時点で `archive/<JST 当日>.html` が
     既に存在すれば以降の step を skip する。LLM コスト（1 run 約 $1-2）と
     ランナー時間（約 27 分）を丸ごと節約できるので Python 側ではなく workflow で
     止める。skip したことは `::warning` に出す（C156 の教訓）
  3. **`workflow_dispatch` に `force` input** —— 意図的な再生成（C174 のような
     ケース）はガードを無効化して通す。`schedule` 起動では inputs が空なので
     常にガードが効く

  #### 8/28 の掃除：どちらを残したか

  **2 回目（遺伝的アルゴリズム / 韓国風ナムル / axismag 718611）を残した。**

  根拠は「履歴は**表示されたもの**に対する dedup・ローテーションを駆動する装置
  であり、何が表示されたかの真実は archive である」。現行の
  `archive/2026-08-28.html` は 2 回目の内容で、上書き型の
  `displayed_urls_2026-08-28.json` も 2 回目と整合している。1 回目を残すと、
  紙面に載っている概念・料理・記事が「まだ出していない」扱いになり、近日中に
  再登場しうる一方、実際には出ていないスピノザが誤って除外され続ける。

  #### 副産物

  workflow の step に `if:` を挿入する際、`Trigger Vercel deploy hook` が
  既に `if:` を持っており **YAML の重複キー**を作ってしまった（後勝ちで
  silently 解決される）。同 step は `steps.commit_push.outputs.committed` に
  依存しており Commit and push が skip されれば発火しないため、挿入した方を
  削除した。テストに重複キーの回帰検査を入れてある。

- **今後の観察ポイント**: 次に schedule が遅延して二重起動したとき、2 本目の run
  が `::warning title=C185 duplicate run skipped` を出して即終了すること。
  出ずに生成まで走ったらガードが効いていない。

  | 表題 | 夏の食卓に、黄色い実の静かな主役 |

  生成は **1 回の JSON 応答**で 5 フィールド全部を出す。`parsed["dish_name"]`

  再生成ループも無い（`call_claude_with_retry` は通信リトライのみ）。

  `_validate` は存在チェックと genre 白名単しか見ておらず、フィールド間の整合を
  一切検査していなかったため素通りした。

  寄与要因が 2 つある:

  1. **前日の食材に引っ張られた** —— 8/19 が「夏トウモロコシとえびの中華風
     薄塩かき玉スープ」。8/20 の本文はとうもろこし。プロンプトの「過去 30 日に
     提案済の料理（避ける）」制約を dish_name 側だけが満たし、body は元の着想の
     まま残ったと読める
  2. **出力順** —— `dish_name → ingredients → genre → column_title → column_body`
     で、料理名の確定と本文執筆の間に 3 フィールド挟まる

  #### 発生頻度: 115 日で 1 日だけ

  材料欄の各要素が本文に出現するかを最長共通部分列比（表記ゆれ吸収）で判定:

  | 未出現件数 | 日数 |
  |---|---|
  | 0 件 | 88 日 |
  | 1 件 | 22 日 |
  | **2 件** | **1 日（8/20）** |

  完全に分離できる。1 件の 22 日は「豚こま切れ」対本文「豚肉」のような表記ゆれで、
  本文は料理名と整合していた。

- **対処 (C178)**: C176 と同じ二段構え。

  1. **プロンプト** —— 出力順を `column_body` 先行に変え、本文からdish_name /
     ingredients を導出させる。「完全に同一の料理を指すこと」を明示し、8/20 の
     実例を ×/○ で載せた。「本文を書いたあとで料理名だけ差し替えない」も明記
  2. **整合チェック** —— 材料欄の未出現が 2 件以上で検知し、**1 回だけ再生成**。
     それでも不整合なら未出現が少ない方を採用して WARN。閾値未満でも件数を
     debug に残す（閾値の妥当性を後から検証するため）

  **静的 fallback には落とさない。** 不整合は表示上の瑕疵であって紙面は成立
  しており、「鮭の塩焼き定食」に落ちる方が損失が大きい（論考休載との違い）。

  #### 判定に料理名を使わなかった理由

  当初は料理名も分割して判定に含めたが、日本語の「と」で分割すると
  **「とうもろこし」が割れる**（「ズッキーニととうもろこし」→「うもろこしの…」）。
  材料欄はカンマ区切りで曖昧さがなく、それだけで 8/20 を完全に分離できたので
  料理名は判定に使わない。

  #### 表記ゆれ吸収は 2 層構造

  マッチャが吸収するのは材料名の過半が本文に出る**軽い**ゆれだけ
  （「夏トマト」対「トマト」= 3/4）。「絹ごし豆腐」対「豆腐」（2/5）や
  「豚こま切れ」対「豚肉」（1/5）は取りこぼすが、実測でこの取りこぼしは
  常に 1 日 1 件以内に収まるので**閾値 2 件が二層目として吸収する**。
  マッチャを緩めると本物の不整合（8/20 の「ベーコン」）まで通ってしまう。

- **今後の観察ポイント**: 8/21 以降、`[cooking] WARN: フィールド不整合を検知`
  が出るか。出て再生成で解消すれば①②とも機能している。debug 行の未出現件数が
  1 件に張り付いたままなら閾値は妥当。2 件が頻発するようなら閾値を上げるか
  マッチャを見直す。

### 慢性 403/405 ソースの棚卸し — 「壊れた」のではなく「GHA から見えない」

- **記録日**: 2026-08-14（C162 の 8/14 検証でログノイズが新規障害を隠す問題として顕在化）
- **観察内容**: 毎朝 6-10 件の fetch 失敗が常態化。うち 4 ソースは慢性的で、
  8/14 の Reuters 503（新規の一時障害）がノイズに埋もれて見えにくくなっていた。
- **実測（2026-08-14、ローカル WSL から default UA / browser UA の両方で検証）**:

  | ソース | GHA | ローカル | server | 採用実績 | 最終採用 |
  |---|---|---|---|---|---|
  | 経済産業省ニュースリリース | 403 | **200 OK** | AmazonS3 | 3 日 | 2026-05-02 |
  | 公正取引委員会 報道発表 | 403 | **200 OK** | AkamaiGHost | 5 日 | 2026-07-03 |
  | ダ・ヴィンチWeb | 403 | **200 OK** | Apache | **0 日** | — |
  | ナタリー音楽 | 405 | **200 OK** | — | **40 日** | 2026-06-29 |

- **真因**: **4 件ともフィードは生きている。GHA runner の IP レンジが弾かれている**。
  UA 変更では回避できない（default UA / browser UA のどちらでもローカルは 200、
  GHA は 403/405）。C130 が JFTC について出した結論
  「UA 起因ではなく IP + UA の合わせ技」が、4 ソース全部に当てはまった。
  - ナタリーだけ 405（Not Allowed）で他 3 件と異なる。CDN が特定のリクエスト
    パターンを拒否している可能性。原因の粒度は違うが、**ローカルで取れて GHA で
    取れない**という構図は同じ
- **JFTC の経緯（C130）**: Sprint 11 で JftcDriver に実ブラウザ寄りの UA を個別
  override して一時的に回避できた。しかし C130 の調査結論そのものが「UA 起因では
  なく IP + UA の合わせ技」であり、恒久解でないことは当時から判明していた。実際、
  修正後に採用できたのは 6/13〜7/03 の 5 日のみで、以降は再び 403。Akamai edge 側の
  ルール更新で無効化されたと見られる。**UA の再変更は同じ轍なので推奨しない**。
  なお `robots.txt` は `User-agent: * Allow: /` で許可的、アクセスポリシー違反ではない。
- **対処（C163）**:
  1. `sources/*.md` の見出しを ❌ にし、`- **fetch_status**: BLOCKED_RUNNER_IP
     （確認日 / C 番号）` フィールドに理由・採用実績・判断根拠を明記
  2. **日次 fetch から除外**（ログノイズの源を断つ）。定義は残す — 実行環境が
     変われば復活しうるため「削除」ではなく「到達不能」として記録する
  3. **週 1 回（月曜）だけプローブ**して復旧を検知する。成功すれば
     `[C163] 到達不能マークの <名前> が N 件取得できました` と目立つログを出し、
     依然ダメでも `[C163] 週次プローブ: 4 件中 復旧 0 / 依然ブロック 4` を出す。
     C156 の教訓（BbcArticleScraper が silently 0 件を返し続けて 10 日以上
     気づかれなかった）を踏まえ、**「静かに諦める」ことをしない設計**にした
- **設計上の区別**: 既存の ❌（The Quietus 閉鎖など**恒久的に死んだ** 6 件）とは
  `BLOCKED_RUNNER_IP` marker で区別する。恒久死は従来どおり `FetchMethod.BLOCKED`
  で driver を呼ばないが、到達不能ソースは**本来の fetch_method を保持**する
  （週次プローブで正しい driver に dispatch する必要があるため）。
- **失われるもの / 代替**:
  - **ナタリー音楽が最も惜しい**（国内音楽ニュースの最頻ハブ、採用実績 40 日で突出）。

  - **JFTC は一次情報の速報性が失われる**。フランチャイズ規制リスクの捕捉は
    Web-Repo 系の他ソースが部分的に担うが、完全な代替ではない
  - 経産省は採用 3 日、ダ・ヴィンチWeb は 0 日で、実害は小さい
- **恒久対策の選択肢**: 実行環境を GHA 以外（自宅サーバ / VPS 等）に移すか、

### 2 面 Headlines 英語ソース（BBC 等）の和訳消失 → 真因は 2 つあった

- **発見日**: 2026-06-29（W6 Day 2 朝刊レビュー）
- **観察当初**: 以前は BBC 等英語ソースが日本語訳で表示されていたが、
  6/29 朝刊では英語のまま表示。神山さん「これって仕様だっけ？」
- **C109 真因究明**（2026-06-30）:
  - 「翻訳機能の回帰」ではなく **「BBC の Page I 採用 → Today's Headlines
    降格」** が真因
  - Page I 採用時: `article-title-japanese` でフル翻訳（5/10 例：
    「デビッド・アッテンボロー卿はどのようにして…」）
  - Today's Headlines 採用時: `_render_todays_headlines` は description
    truncate のみ、翻訳経路なし（6/28 例：「Lithium battery fires...」）
  - Sprint 9 改革（C42 / C75 / C76 / C79）によるソース多様化の自然な結果
- **神山さん判断**: 選択肢 C（仕様として受容、様子見）

#### ⚠️ C155a / C156 追記（2026-08-10）— **真因は 2 つあった**

C109 の調査は「Page I 降格」を真因と結論づけたが、**もう 1 つ独立した原因が
並行して存在していた**ことが C155a のコスト調査で判明した。

- **真因 1（C109 で特定済）**: Page I 降格による翻訳経路の喪失。
  Headlines のレンダラにはタイトル翻訳が無い
- **真因 2（C155a で新たに判明）**: **`BbcArticleScraper` の破損**。
  Headlines には「BBC 記事のみ本文を取得して Haiku で 250-350 字の日本語
  要約を付ける」経路（`generate_summary_with_llm`）が Sprint 7 Phase 2 で
  実装されていたが、これが**動いていなかった**

  - `scripts/lib/drivers/html.py` の `sc-` prefix 正規表現が BBC の CSS 変更で
    当たらなくなり、段落抽出が **silently 0 件**を返す状態
  - 本文 0 件 → `BODY_MIN_CHARS=400` 未満 → `format_summary()`（description の
    truncate）に fallback
  - 実測: `page2.headlines_summary` タグの LLM 呼び出しが **2026-08-01〜08-10
    の 10 日間で 0 件**。7/13〜7/22 の 10 日間も 0 件
  - 8/10 紙面の実物: `It's lurking in one of the US's top exports: higher education`
    （英語 description がそのまま）

- **なぜ C109 時点で気づけなかったか**: 0 件返却が silent だったため、
  呼び出し側から見ると「本文が短い記事」と区別がつかず、fallback に落ちる
  だけで何のログも出なかった。`scripts/SUMMARY.md` §12 は
  「BBC が sc- prefix を変えた場合：silently 0件返却」と **failure mode を
  正確に予見していた**が、検知手段が無かった
- **教訓**: fallback は紙面を守るが、**fallback したこと自体を記録しないと
  破損が可視化されない**。C155 で新設した `page5/article_summarizer.py` は
  fallback 時に必ず stderr へ理由を出すようにしてある

- **対処**:
  - C155（2026-08-16 切替）で Today's Headlines を枠ごと廃止 → 実害は消滅
  - C156 で `BbcArticleScraper` を deprecated 明示 + 0 件時に
    `BROKEN` / `EMPTY` を切り分けて warn。`DeprecationWarning` も送出
  - 唯一の import 元は Phase 1 レガシー `scripts/regen_front_page.py`
    （cron / GHA から実行されない使い捨てスクリプト）。修正は別途判断
- **将来検討**: 本文抽出を復活させるなら CSS クラス名依存をやめ、構造ベース
  抽出か Readability 系ライブラリの導入が必要。BBC 以外にも効かせたいなら後者
- **状態**: 完了（C155 で枠ごと廃止 + C156 で deprecated 化）
- **関連 commit**: C109 調査結果報告のみ / C155 (`574fc57`) / C156
